# License evidence and copyleft decisions for fast-mlsirm 0.11.5

Date: 2026-09-23. Cargo evidence was taken at `main` 27086529. Python evidence
was taken after the NumPy lock reconciliation in this change. The raw
per-package inventory is
[`license-evidence-0.11.5/inventory.json`](license-evidence-0.11.5/inventory.json).
It was generated by [`tools/license_inventory.py`](../../tools/license_inventory.py)
(the reproduction steps are at the end of this document).

## 1. Governing policy

- GPL, LGPL and AGPL dependencies are replaced, either by a permissively
  licensed alternative or by an independent implementation. Copyleft source is
  never copied or translated. A target that is not executed does **not**
  exempt a dependency by itself.
- A dual- or multi-licensed dependency is allowed only when this repository
  records why the permissive option was chosen.
- UNKNOWN is on hold and is never assumed to be permissive.
- The license of existing code is never relabelled. Removing functionality,
  such as dropping NumPy, is not an acceptable fix.

Primary evidence from the currently published release, 0.11.4 (13 files on
PyPI, sha256 verified against the PyPI JSON):

- Each wheel contains only `fast_mlsirm/*.py`, the compiled
  `fast_mlsirm/_core.*` extension, the project's own MIT `LICENSE`, the
  CycloneDX SBOM `sboms/fast-mlsirm-py.cyclonedx.json` and the dist-info
  bookkeeping files. **No third-party shared library is vendored**: there is no
  `.libs/`, `.dylibs/` or bundled DLL.
- The sdist contains only this repository's `python/`, `tests/`,
  `crates/mlsirm-core`, `crates/fast-mlsirm-py`, `Cargo.toml`, `pyproject.toml`,
  `README.md` and `LICENSE`. It carries no third-party source.
- `_core` links dynamically only to operating-system libraries:
  - Linux: `readelf -d` NEEDED lists `libgcc_s.so.1`, `libm.so.6`, `libc.so.6`
    and `ld-linux-x86-64.so.2`.
  - macOS: `otool -L` lists `libSystem`, `libobjc`, `libiconv` and the
    CoreFoundation, CoreGraphics, Foundation, Metal and QuartzCore frameworks.
  - Windows: the DLL imports are Windows, D3D12 and Vulkan system DLLs plus
    `vcruntime140.dll`.

  The manylinux policy guarantees that these libraries exist on the host
  system, and none of them is shipped.
- The wheel's embedded SBOM, taken from a 0.11.4 wheel rebuilt on s1 with
  maturin 1.14.1, has 157 components plus the root. That equals the 158
  packages of the binding-crate lock graph exactly, with no difference in
  either direction.

The **published artifact scope** is therefore the binding-crate lock graph
(`crates/fast-mlsirm-py/Cargo.lock`, 158 packages) plus this repository's own
Python and Rust source. NumPy is the single runtime `Requires-Dist`. It is not
inside any published artifact. The user installs it separately from PyPI, and
section 6 covers it.

## 4. Verdict: atheris 3.1.0 is Apache-2.0 (metadata gap recorded, not assumed)

- PyPI metadata for 3.1.0 has `license = null`, `license_expression = null`
  and no License classifier. By metadata alone it is **UNKNOWN**, and the
  inventory keeps `license_class_from_metadata = "UNKNOWN"`.
- The project's own source: upstream `google/atheris` has **no `3.1.0` tag**.
  The release is commit `352d5f29d811e0b51807ca57ed5551dd08ece528`
  ("Bump Atheris to 3.1.0 for CPython 3.14 support", 2026-06-16).
  - `setup.py` at that commit sets `__version__ = "3.1.0"`, carries the
    Apache-2.0 header, and passes no `license=` or classifiers. That is the
    root cause of the metadata gap.
  - Its `LICENSE` is the Apache License 2.0, sha256
    `58d1e17ffe5109a7ae296caafcadfdbe6a7d176f0bc4ab01e12a689b0499d8bd`.
- The artifact: all three PyPI 3.1.0 wheels (cp312/cp313/cp314,
  manylinux2014 x86_64; no sdist exists) contain
  `atheris-3.1.0.dist-info/licenses/LICENSE` with the **same sha256**.
- Bundled native pieces: the wheel also ships `libclang_rt.fuzzer_no_main.a`,
  `asan_with_fuzzer.so`, `ubsan_with_fuzzer.so` and `ubsan_cxx_with_fuzzer.so`.
  These are LLVM compiler-rt/libFuzzer, built by the upstream recipe
  (`deployment/Dockerfile` at 352d5f2 clones and builds `llvm-project`).
  LLVM compiler-rt is `Apache-2.0 WITH LLVM-exception` (upstream
  `compiler-rt/LICENSE.TXT`, sha256
  `1a8f1058753f1ba890de984e48f0242a3a5c29a6a8f2ed9fd813f36985387e8d`). The
  wheel carries **no notice for them**. That is a permissive-notice gap on
  atheris's side, not copyleft.
- **Verdict:** Apache-2.0 for atheris, and Apache-2.0 WITH LLVM-exception for
  its bundled compiler-rt. Both are permissive. The determination comes from
  the LICENSE file (hash-matched source to artifact), and the inventory marks
  it as an explicit evidence-based exception
  (`license_determination.origin`), not an inference from the missing field.
  Scope: optional extra `fuzz` and the fuzz CI job; outside every published
  artifact.
- Upstream fix: a `license="Apache-2.0"` / `license-expression` entry in
  atheris `setup.py`. This is a follow-up, because google/atheris requires a
  Google CLA for pull requests.

## 5. Verdict: r-efi 5.3.0 and 6.0.0 are used under MIT (elected, with rationale)

- Declared: `MIT OR Apache-2.0 OR LGPL-2.1-or-later` for both versions.
- **Neither `.crate` contains a LICENSE file.** The grant text is in `AUTHORS`,
  which has a `LICENSE:` triple-license statement followed by the full MIT
  permission text (`AUTHORS-MIT`), the Apache-2.0 notice (`AUTHORS-ASL`) and
  the LGPL-2.1+ notice (`AUTHORS-LGPL`).
  - 5.3.0: `.crate` sha256 `69cdb34c…754b0f` (= `Cargo.lock` checksum),
    `AUTHORS` sha256 `ff92bed4…f5dda7`.
  - 6.0.0: `.crate` sha256 `f8dcc9c7…a0d9bf` (= `Cargo.lock` checksum),
    `AUTHORS` sha256 `d027e91d…d96111`.
- Distribution check: each crate's `.cargo_vcs_info.json` points at upstream
  `r-efi/r-efi` tag `v5.3.0` (`97b55bed1c2c91dcbf787674849f05337ff80b33`) and
  tag `v6.0.0` (`7e1b0322d31d625f81a5656096330934f9cd835d`). At both tags the
  tree has no LICENSE/COPYING file, and `AUTHORS` is byte-identical to the
  crate's copy. `README.md` states the same triple license.
- Where it enters: from the root workspace lock only, through
  `mlsirm-core [dev-dependencies] → proptest 1.11.0`:
  - 5.3.0: `→ rand 0.9.4 → rand_core 0.9.5 → getrandom 0.3.4 → r-efi 5.3.0`
  - 6.0.0: `→ tempfile 3.27.0 → getrandom 0.4.3 → r-efi 6.0.0`

  (`cargo tree -i r-efi@<v> --target all -e all`.) It is absent from the
  binding lock graph and the wheel SBOM **because it is a dev-dependency
  path**. That is the scope fact recorded here. "Not compiled for our targets"
  is not used as an exemption argument, and both rows stay in the inventory.
- **Election: MIT.** Rationale: it is one of the three licenses the authors
  grant; it matches fast-mlsirm's own license; it has the smallest obligation
  set; and its full permission text is present in the distributed `AUTHORS`
  file, so the elected grant is evidenced by the artifact itself.
  LGPL-2.1-or-later is not exercised.

## 6. NumPy

### 6.1 Lock reconciliation (fixed in this change)

Before this change there were three versions:

- `uv.lock` pinned 2.5.1;
- the hash-locked `requirements/ci.txt` and `requirements/package.txt`
  pinned 2.5.2;
- the audit environment had 2.5.3, the latest release (2026-09-06).

All three locks now pin **numpy 2.5.3**.

- `uv lock --upgrade-package numpy==2.5.3 --no-build` changed only the numpy
  entry.
- In both requirements files only the numpy block was replaced. The old block
  was verified to equal the complete 2.5.2 PyPI file set (66 hashes), and the
  new one is the complete 2.5.3 set (66 sha256 hashes: cp312 to cp315 wheels on
  all platforms, plus the sdist).
- The user-facing constraint `numpy>=1.24` in `pyproject.toml` is unchanged.

The published wheels and sdist are built by `maturin-action` without
installing Python NumPy: the Rust `numpy` crate needs no Python NumPy at build
time. The artifacts are therefore NumPy-version-independent. The locks feed CI
(`ci.txt`), the release-evidence package job (`package.txt`) and developer
environments (`uv.lock`).

### 6.2 What the official NumPy 2.5.3 wheels bundle

Each cp312 wheel was downloaded from PyPI and its sha256 verified. The
evidence comes from the file contents and `readelf -d` / `otool -L`, not only
from the notice stanzas.

| numpy wheel (platform a fast-mlsirm user on that platform receives) | Vendored libraries | Linking | License of the vendored GCC pieces |
| --- | --- | --- | --- |
| manylinux x86_64 (**our Linux x86_64 wheels**) | `libscipy_openblas64_`, `libgfortran.so.5`, **`libquadmath.so.0`** | dynamic, loaded at `import numpy`: `_multiarray_umath → libscipy_openblas64_ → libgfortran → libquadmath` (DT_NEEDED) | libgfortran: GPL-3.0-or-later WITH GCC-exception-3.1; **libquadmath: LGPL-2.1-or-later, no runtime exception** |
| manylinux aarch64 (**our Linux aarch64 wheels**) | `libscipy_openblas64_`, `libgfortran.so.5` | dynamic (`_multiarray_umath → openblas → libgfortran`) | GPL-3.0-or-later WITH GCC-exception-3.1 (no libquadmath on aarch64) |
| macOS 10.13 x86_64 / 11.0 arm64 (macOS < 14) | `libscipy_openblas64_`, `libgfortran.5`, **`libquadmath.0`**, `libgcc_s.1.1` | dynamic (`@loader_path`, `otool -L`) | GCC exception + **LGPL-2.1-or-later** |
| macOS 14.0 arm64 / x86_64 (macOS ≥ 14) | **none**; links Apple Accelerate | system framework | none |
| win_amd64 (**our Windows wheels**) | `libscipy_openblas64_*.dll`, `msvcp140*.dll` | libgfortran **statically** linked into the OpenBLAS DLL (stanza "statically linked"; the DLL contains `gcc-10.3.0/libgfortran` paths); no libquadmath markers | GPL-3.0-or-later WITH GCC-exception-3.1 |
| musllinux x86_64 / aarch64 | adds `libgcc_s` and `libstdc++` (**no notice stanza** in NumPy's LICENSE.txt for these two); x86_64 also has libquadmath | dynamic | GCC exception; libquadmath LGPL-2.1-or-later |
| win_arm64 | `scipy_openblas*.dll` built with the **LLVM flang 20.1.8 runtime** (Apache-2.0 WITH LLVM-exception), `msvcp140` | static flang runtime | **no GCC component** |
| win32 | none (lapack_lite) | none | none |

Notes:

- NumPy's `LICENSE.txt` is templated and **over-declares**. The macOS 14 and
  aarch64 wheels carry the libgfortran/libquadmath stanzas even though they
  bundle nothing or no libquadmath. The inventory is built from the files that
  are actually present.
- libquadmath's license was checked at the GCC source:
  `libquadmath/COPYING.LIB` (LGPL-2.1, sha256 `32434afc…d2f2b`), and headers
  such as `quadmath.h`, `math/expq.c` and `printf/printf_fp.c` say
  "GNU (Library|Lesser) General Public License … version 2(.1) or later". The
  GCC Runtime Library Exception (`COPYING.RUNTIME`) applies to libgfortran and
  libgcc/libstdc++, **not** to libquadmath.
- NumPy's top-level `License-Expression`
  (`BSD-3-Clause AND 0BSD AND MIT AND Zlib AND CC0-1.0`) mentions none of the
  GCC components.

### 6.3 Verdict: DECISION REQUIRED (not approved)

- NumPy itself is permissive.
- The official NumPy wheels that fast-mlsirm users receive on **Linux x86_64
  and macOS < 14** bundle and dynamically load **libquadmath
  (LGPL-2.1-or-later)**. This is a genuine LGPL component in the runtime
  dependency closure.
- On every platform except macOS ≥ 14, the wheels also carry the GCC runtime
  libraries (libgfortran, and on some platforms libgcc_s/libstdc++), which are
  **GPL-3.0-or-later WITH GCC-exception-3.1**. This change **does not approve**
  that exception; it is surfaced for an owner decision.
- fast-mlsirm does not redistribute any of these. NumPy's own wheels do, and
  users obtain them through `Requires-Dist: numpy>=1.24`. Only 2.5.3 was
  inspected. Other versions allowed by `>=1.24` were not.

### 6.4 Replacement assessment (NumPy stays; functionality preserved)

1. **Fortran-free OpenBLAS for NumPy wheels.** This removes libgfortran and
   libquadmath entirely. Two ways to get it:
   - OpenBLAS can build LAPACK from its C translation (`C_LAPACK=1`, no
     Fortran compiler, BSD-3-Clause).
   - It can be compiled with LLVM flang, whose runtime is Apache-2.0 WITH
     LLVM-exception. The NumPy 2.5.3 **win_arm64 wheel already does this**,
     which shows the scipy-openblas toolchain supports it.

   Either route means building and hosting NumPy wheels (for example, on a
   project index) for the four supported platforms. That is a separate
   project with CI, provenance and parity-test cost, **not started here**.
2. **Accelerate on macOS ≥ 14** is already clean. It can be documented as the
   recommended macOS baseline, but it does not fix Linux.
3. **Upstream request** to NumPy / scipy-openblas to ship Fortran-free x86_64
   wheels. This costs us nothing, but its outcome is uncertain.
4. **Not acceptable:** dropping NumPy (a policy violation and a loss of
   functionality), or pinning `numpy` to a version range. Only 2.5.3 was inspected, and there is
   no evidence that any official Linux x86_64 NumPy wheel is libquadmath-free.

Recommendation (tracked in #2136): a follow-up that combines (3) now with (1) as a
Fortran-free (`C_LAPACK`) scipy-openblas → NumPy wheel build for
manylinux x86_64/aarch64 and win_amd64, keeping Accelerate on macOS ≥ 14. The
owner decides whether the GCC-runtime-exception libraries are acceptable
until then.

1. **No third-party notices ship in the wheel.** `_core` statically links 77
   to 89 third-party crates per target (MIT, Apache-2.0, ISC, Zlib, BSD-2,
   Unicode-3.0). Those licenses require their notices to go with binary

   the SBOM. Proposed fix: generate a `THIRD_PARTY_LICENSES` file from the
   binding lock and include it in the wheel and sdist. Tracked in #2137.
2. **objc2 / Apple SDK caveat** (section 3), for the owner's review. Tracked in #2137.
3. **hypothesis is MPL-2.0 (file-level weak copyleft).** It is dev/test only
   and outside the user's GPL/LGPL/AGPL set, so it is recorded here for owner
   confirmation, not removed.
4. **Other Python lock drift** (not changed here, because the task scoped the
   reconciliation to NumPy):
   - hypothesis is 6.156.6 in `uv.lock` but 6.168.0 in `ci.txt`;
   - maturin is 1.15.0 in the locks but 1.14.1 in `publish-pypi.yml`;
   - the `ci.txt` header records a `--no-index` pip-compile invocation.
5. **The GitHub dependency-graph SBOM** is based on the default branch and has
   25 NOASSERTION rows (numpy, maturin, pytest, action pins, ranged Rust
   entries). It is not the release SBOM. The per-artifact SBOM is the wheel's
   embedded CycloneDX file.
6. **System linking** of `_core` to glibc (LGPL-2.1-or-later) and `libgcc_s`
   (GCC exception) on Linux is common to every CPython extension and is not
   shipped. It is recorded here and **not auto-approved**; it goes in the same
   owner decision as section 6.3.
7. **No CI gate enforces this policy yet.** A cargo-deny `[licenses]` allow
   list with an explicit `r-efi` clarification, plus a fail-closed Python
   license check over the locks, would keep this evidence from going stale.
   Tracked in #2138, together with items 3 and 4 and the atheris upstream
   metadata fix.

## 8. Reproduction

The Cargo steps ran on s1 in an isolated directory with its own `CARGO_HOME`
and `CARGO_TARGET_DIR`. The Python steps can run anywhere.

```bash
cargo metadata --locked --format-version 1 > ws.json
cargo metadata --locked --format-version 1 --manifest-path crates/fast-mlsirm-py/Cargo.toml > py.json
for t in x86_64-unknown-linux-gnu aarch64-unknown-linux-gnu x86_64-apple-darwin aarch64-apple-darwin x86_64-pc-windows-msvc; do
  cargo tree --locked --manifest-path crates/fast-mlsirm-py/Cargo.toml --features pyo3/extension-module \
    --target $t -e normal,no-proc-macro --prefix none -f "{p}" | sed 's/ (\*)//; s/ (proc-macro)//' | awk '{print $1"@"$2}' | sort -u > tree/linked-$t.txt
  cargo tree --locked --manifest-path crates/fast-mlsirm-py/Cargo.toml --features pyo3/extension-module \
    --target $t -e normal,build --prefix none -f "{p}" | sed 's/ (\*)//; s/ (proc-macro)//' | awk '{print $1"@"$2}' | sort -u > tree/build-$t.txt
done
maturin build --release --out dist            # take dist-info/sboms/*.json as sbom.json
# PyPI: fetch https://pypi.org/pypi/<name>/<version>/json into pypi-meta/<name>-<version>.json and
# download the wheels (numpy: every cp312 wheel; atheris: all), verifying sha256 against that JSON.
python tools/license_inventory.py \
  --cargo-metadata-workspace ws.json --cargo-metadata-binding py.json \
  --cargo-lock Cargo.lock crates/fast-mlsirm-py/Cargo.lock --cargo-registry-src "$CARGO_HOME/registry/src" \
  --wheel-sbom sbom.json --tree-dir tree --uv-lock uv.lock \
  --requirements requirements/ci.txt requirements/package.txt \
  --extra-python "maturin==1.14.1:publish-pypi.yml maturin-action binary" \
  --python-scope docs/security/license-evidence-0.11.5/python-scope.json \
  --pypi-meta-dir pypi-meta --pypi-artifact-dir pypi-art \
  --out docs/security/license-evidence-0.11.5/inventory.json
```
