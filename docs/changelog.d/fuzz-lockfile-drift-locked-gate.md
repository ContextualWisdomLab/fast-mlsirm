# Pin the fuzz crate's dependency graph and gate it in CI

## Fixed

- `fuzz/Cargo.lock` had not been regenerated since 2026-07-10 and still described a 12-package graph around `mlsirm-core 0.1.0`, while `crates/mlsirm-core/Cargo.toml` (now 0.9.1, with the wgpu GPU kernels) had moved on. `cargo metadata --locked --manifest-path fuzz/Cargo.toml` fails on that lockfile, so every ClusterFuzzLite `cargo fuzz build` silently re-resolved 137 missing packages to whatever crates.io served that day: the fuzz target was neither reproducible nor pinned to the versions the workspace tests run against. The lockfile is regenerated by seeding it from the workspace `Cargo.lock` and resolving only the fuzz-only chain on top (`libfuzzer-sys`, `arbitrary`, `cc`, `jobserver`, `find-msvc-tools`, `shlex`, `fast-mlsirm-fuzz`): every crate shared with the workspace resolves to the identical version (0 mismatches across 144 shared packages), nothing was removed, and `--locked` now passes.
- The `rust` CI job now runs `cargo metadata --locked --manifest-path fuzz/Cargo.toml`, so the fuzz lockfile drifting from `fuzz/Cargo.toml` or from the `mlsirm-core` path dependency fails a required check instead of being repaired invisibly at fuzz-build time. RED on `main@ce65339f` (the command fails), GREEN on this branch. No fuzz target, harness, likelihood, or Rust numerical behavior changes.
