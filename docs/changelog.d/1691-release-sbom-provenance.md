# Release SBOM and builder-local provenance

## Fixed

- Release evidence now requires builder-local provenance for the sdist and every wheel plus a separately published SPDX JSON source-release SBOM generated from the exact reviewed release commit. GitHub release and PyPI publication are both gated on successful SBOM generation, validation, and attestation, while the PyPI upload set remains restricted to package distributions. The repository-owned SBOM gate parses the generated document fail closed, rejects non-standard numeric constants and duplicate JSON object members, and replays the mandatory SPDX 2.3 document-creation envelope (`SPDX-2.3`, `CC0-1.0`, `SPDXRef-DOCUMENT`, non-blank single-line document name, absolute fragment-free namespace URI restricted to RFC 3986 literal characters plus valid percent escapes, exact second-resolution UTC `YYYY-MM-DDThh:mm:ssZ` creation timestamp, and at least one non-blank single-line creator identity) before attestation/publication. Raw non-ASCII, control, and backslash namespace characters are rejected rather than accepted by Python's non-validating URL splitter; percent-encoded UTF-8 remains admissible. For repositories with GitHub release immutability enabled, the release tag workflow now creates the GitHub release as a draft, the publication workflow independently requires exactly one matching unpublished draft before any build or destructive retry, attaches distributions and the standalone SBOM while that draft is still mutable, and a finalizer publishes the release only after both asset upload and PyPI publication succeed; this prevents immutable publication from sealing an empty release before its required assets can be attached and prevents direct workflow dispatch from applying draft-recovery semantics to a published release. Because build and matrix work can outlive the initial admission check, every irreversible publication seam now repeats that authenticated exact-draft check immediately before GitHub asset replacement, PyPI publication, or draft finalization; an early observation of mutable state is not treated as durable authorization for a later write. Same-name release assets are replaced only while the release is still a draft, so a retry after a successful asset sink but failed PyPI sink does not deadlock on the previous draft assets; no asset replacement is attempted after final publication. A PyPI retry after a partial upload now queries the release-specific PyPI JSON API, requires every already-published filename to exist in the reviewed local artifact set with the identical SHA-256 digest, removes only those proven-identical files from the retry upload directory, and uses the pinned uploader for the remaining files without enabling broad duplicate suppression. After upload, the workflow requires PyPI to expose exactly the complete reviewed filename/SHA-256 set before GitHub release finalization; unexpected filenames or digest mismatches fail closed. Immediately before the final draft-to-published transition, the finalizer now re-downloads the exact package and SBOM artifacts from the same workflow run and compares their filename set, SHA-256 digests, byte sizes, and uploaded state with the authenticated GitHub release-asset representation; missing, duplicate, unexpected, non-uploaded, digest-mismatched, or size-mismatched draft assets fail closed instead of being sealed into the immutable release. The evidence scope and primary-source basis are documented explicitly; the standalone source-tree SBOM is not misrepresented as a per-wheel SBOM predicate or as proof of a SLSA Build Level. The newly introduced SBOM and finalizer jobs use the repository's explicit Ubuntu 24.04 Linux runner contract rather than reintroducing the moving `ubuntu-latest` alias owned by the separate runner-pinning lane.
