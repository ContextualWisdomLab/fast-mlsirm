# GPU evidence acquisition boundary

## Changed

- Record the repository-owned software-Vulkan evidence path that replaced the earlier live package-acquisition failure. The controlled Ubuntu 24.04 lane consumes the image-bundled Chrome SwiftShader payload, opts into wgpu's non-compliant software-adapter flag only inside that evidence lane, validates the driver files, records SHA-256 identity, and uses `VK_DRIVER_FILES`. Ordinary production callers keep wgpu's compliant-adapter default.
- Replace the former marginal GPU resource topology that required 17 storage buffers for the E-step and 18 for scoring on a SwiftShader adapter exposing 10 storage buffers per shader stage. Read-only floating inputs are packed into one `f32` arena, integer/CSR inputs into one `u32` arena, and score outputs into one output arena. The resulting E-step layout is 8 storage bindings plus one uniform; score is 3 storage bindings plus one uniform. Checked element offsets in the uniform contract preserve logical array boundaries.
- Check packed storage-binding size and total buffer size against the actual adapter before creating buffers. The controlled adapter probe requires at least 8 storage slots, one uniform slot, and 9 combined buffer/acceleration-structure slots while recording size, alignment, and workgroup limits for diagnosis. Whole-buffer arena indexing does not use dynamic storage binding offsets.
- Keep acceptance execution-based. The ordinary PR GPU lane must create the real pipelines on the controlled SwiftShader adapter, execute `tests/test_marginal_parity.py::test_marginal_gpu_agrees_with_cpu_loosely` without CPU fallback or skip, and pass the zero-skip JUnit gate. The scheduled paper-design recovery lane must use the same adapter setup for its Rust GPU recovery study. Missing image payloads, resource-limit violations, or pipeline/parity failures remain RED rather than being converted to fallback evidence.
